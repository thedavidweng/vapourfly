# Generator playlist slots use stable ids and overwrite

Discover, Dynamic Templates, and Editorial Moods are generators that produce Playlists. In the GUI, a successful generate **writes** the result to the local playlist store under a **stable playlist id** per generator identity (one Discover slot, one slot per Dynamic Template, one slot per Editorial Mood) and **overwrites** that slot on regenerate. Users are not prompted to name each generation; long-term keep is done by changing id/name and saving again. Trade-off: store stays small and “latest generation” is always addressable for match/sync, but a regenerate destroys the previous slot contents unless the user re-saved under a new id. Rejected alternatives: timestamped ids every run (history clutter), confirm-before-overwrite on every generate (breaks one-click generate), and preview-only without store write (dead-end UX and inconsistent with “Generate playlist” language). Core scoring and eligibility stay in domain modules; the GUI owns slot identity and write timing. CLI behavior is not required to mirror slots unless a later change explicitly aligns it.
